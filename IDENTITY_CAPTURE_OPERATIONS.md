## Storage / access

0700), code HMAC, identity key and pseudonymous claim/done markers. It is not a second identity
DB. Raw provider subject exists only in process memory and dedicated Secret Manager candidate.
No body, raw subject or reply token is stored in local claim markers.

Dedicated Secret Manager items in project zhongyuan-fude-v2:

No external debug endpoint reveals the code or candidate. SA credentials are never printed.

## Failure / disable / rollback

Reserved identity-verification messages are swallowed even when disabled, expired, malformed,
wrong-code or in a group, so they never reach V1 replies or Sheets query logs. All other traffic
uses the existing V1 flow without requiring capture storage/config. Mixed batches process unrelated
V1 events independently. Capture errors emit only identity_capture_pending_operator_review and
ACK the webhook, avoiding batch retries/duplicate V1 side effects. Operator inspection is mandatory
for an unknown result; identity capture is intentionally not an automatic retry queue.

The durable exclusive claim is written and fsynced before the secret write. Only one candidate can
win across concurrent workers/restart. Timeout/crash after claim burns the code and prevents any
second write. `reconcile` reads the exact candidate in memory, checks claim fingerprint and scoped
identity HMAC, then marks success and closes capture; it never prints raw identity. Do not delete
claims or re-run put to recover an unknown result. Missing/mismatching remote record stays closed
for manual review. New sessions require a separately reviewed recovery, not resetting the old code.

Use `close` for immediate operational rollback; leave code deployed to suppress late redeliveries.
Before reverting the source to the recorded SHA, stop all tester sends and review late redelivery
risk: the old version does not suppress verification messages. Preserve claim/config files on disk.
No database rollback, webhook change or V2 Chat change is needed.
